# 대회 글 구성 표준 — 설계

- 작성일: 2026-08-19
- 상태: 설계 확정 대기 (운영자 시안 승인 완료, 스펙 리뷰 전)
- 범위: 대회 글의 화면 구성 표준 + `validate` 기계 강제 + 신발 브릿지 조건 완화 + 신규 글 slug 규칙
- 시안: `docs/superpowers/design/2026-08-19-race-page-mockup.html` (아티팩트로도 발행됨)

## 1. 배경

운영자 요청은 "대회 글 구성 리뉴얼"이었다. 착수 시점의 내 판단은 **"구성은 이미 일관되니 건드릴 이유가 약하다"** 였고, 그 판단은 **틀렸다.**

틀린 이유가 이 문서의 출발점이다. 나는 `grep`으로 HTML 구조만 봤다. `<h2>` 목록과 `class="tldr"` 유무는 세 글이 거의 같았으므로 "템플릿이 있다"고 결론지었다. 실제 화면을 모바일 폭으로 열어 보니 **같은 템플릿을 쓴다고 믿었던 글들이 서로 다르게 쓰여 있었고**, 공통으로는 같은 정보를 다섯 번 반복하고 있었다.

**교훈: 전달력은 구조 검색으로 판정할 수 없다. 렌더된 화면을 봐야 한다.**

## 3. 실측 근거

### 3-1. 신발 브릿지가 절반 이상 꺼져 있다

`page.tsx:266` 의 `hasShoeLink` 는 본문에 `/shoes/` 가 **하나라도** 있으면 브릿지 전체를 `null` 로 만든다.

| 상태 | 편수 |
|---|---|
| 브릿지 켜짐 (신발 링크 0) | 34 |
| 브릿지 꺼짐 (신발 링크 1+) | **38 (53%)** |
| └ 그중 링크 **1~2개뿐**인데 꺼진 글 | **14** |

브릿지가 켜지면 `shoe-bridge.tsx:73,102` 기준 **신발 카드 최대 4장 + (장거리면) 젤 카드 2장**이 렌더된다. 꺼지면 0장이다.

### 3-2. 링크 1~2개 글은 "기본 세트의 수동 복제"다

임계값을 정하기 위해 링크 1~5개 글의 실제 신발 목록을 봤다.

| 링크 수 | 성격 | 예 |
|---|---|---|
| 1~2개 | **기본 세트 반복** | `nike-pegasus-42 + brooks-ghost-17` 이 3편에, `hoka-clifton-10 + new-balance-1080-v14` 가 2편에 |
| 3개 이상 | **맥락 큐레이션** | 아식스 스폰서 대회에 아식스 4종 · 트랜스제주에 트레일화 5종 · 보스턴 BQ에 레이싱화 3종 |

즉 1~2개는 브릿지가 자동으로 할 일을 손으로 한 것이라 **대체해도 잃는 것이 없고**, 3개 이상은 브릿지가 낼 수 없는 맥락이라 **건드리면 안 된다.**

### 3-3. 같은 정보가 다섯 번 나온다 (육안)

부산브릿지마라톤 글에서 `접수 8/24 10시 · 12,000명 선착순 · 4:30 자격` 세 가지가 나오는 곳:

1. 썸네일 이미지 안
2. 마감 스트립
3. 3줄 요약
4. 개요표
5. 본문 h2 "풀코스는 자격제다"

독자는 **네 화면을 넘겨도 새 정보를 만나지 못한다.** 반면 이 글에만 있는 정보(코스: 오르막 3회·12월 해상 바람·해안선 경관)는 **여섯 번째 화면**에 있다.

### 3-4. 손으로 적은 값은 이미 낡았다

라이브 마감 스트립은 **"접수 시작 D-12"** 로 서 있다. 글 작성일(8/12) 기준으로 손으로 적은 값이고, 관찰 시점(8/19)에는 **D-5**가 맞다. **일주일 틀린 상태로 배포되어 있다.**

이미지는 더 낡는다 — 10월 비교글 썸네일은 **"6개"** 인데 제목은 **"7개"** 다. 글을 갱신할 때 이미지가 따라가지 않았다.

이 두 관찰이 **"이미지 카드뉴스를 만들지 않는다"** 는 결정의 근거다(9절).

### 3-5. 표준이 없어 글마다 편차가 크다

| | 썸네일 역할 | 상태 배지 |
|---|---|---|
| 부산브릿지 | 제목을 그대로 반복 | 없음 |
| 10월 비교 | 제목과 **수치 불일치**(6 vs 7) | 없음 |
| 도쿄마라톤 | 제목에 없는 정보 보완 | **있음** (🔴 접수중) |

도쿄 글은 꽤 좋고 부산 글은 5중 반복이다. **문제는 "구성이 나쁘다"가 아니라 "표준이 없다"** 이다. 그래서 이 설계의 핵심은 새 레이아웃이 아니라 **기계로 강제되는 표준**이다.

## 4. 설계 원칙 — 표면마다 다른 일을 시킨다

지금은 다섯 표면이 같은 일을 한다. 각 표면에 하나의 역할만 준다.

| 표면 | 지금 | 표준 |
|---|---|---|
| 화면 제목 | 검색용 전체 제목(3줄) | **별도 필드**(`displayTitle`) 40자 이하 |
| 상태 배지 | 없거나 제각각 | **날짜에서 자동 계산** |
| 행동 스트립 | 접수 정보 요약 | **지금 할 행동 하나** |
| 핵심 카드 | (없음, 썸네일이 대신) | 날짜·집결·종목·정원·참가비·제한시간 |
| 차별점 블록 | 맨 아래 불릿 | **위로** — 이 대회에만 있는 것 |
| 본문 h2 | 스펙 재서술 | **판단·해석만** |
| 전체 요강표 | 상단 | **맨 아래** — 스펙의 유일한 출처 |
| 3줄 요약 | 접수 정보 반복 | **폐지** |

### 화면 제목은 자동 파생하지 않는다

처음에는 "검색 제목의 파이프(`|`) 앞부분을 화면 제목으로 쓴다"고 설계했으나 **실제 데이터에서 깨진다.** 부산브릿지 글의 파이프 앞부분은

> 국내 첫 트리플 브릿지 풀코스 — 부산브릿지마라톤 2026 접수 8월 24일 10시 시작

로 이미 43자다. 접수 정보가 제목 중간에 박혀 있어 어떤 구분자로 잘라도 화면 제목이 되지 않는다. 시안에서 실제로 쓴 것은 24자짜리 **손으로 쓴 문장**이었다.

따라서 `displayTitle` 은 **별도 필드로 손으로 쓴다.** 썸네일 카피(`scripts/thumbnail/copy.ts`)가 같은 이유로 `OVERRIDES` 를 두고 있다 — 자동 파생은 초안일 뿐이라는 그 파일의 주석이 여기에도 그대로 적용된다.

핵심은 **"사무 → 이야기" 순서를 "이야기 → 사무"로 뒤집는 것**이다. 검색해서 들어온 사람은 접수일을 이미 알고 왔거나(그래서 검색함) 배지·행동 스트립에서 3초 안에 얻는다. 그가 모르는 것은 **이 대회가 어떤 대회인가**이다.

## 5. 데이터 설계 — `raceMeta`

새 표준은 **`raceMeta` 필드를 가진 글에만** 적용된다. 기존 70편은 이 필드가 없으므로 자동으로 검사 대상 밖이다. **"앞으로 쓰는 글부터"가 규칙이 아니라 구조로 보장된다** — 이것이 이 설계에서 가장 중요한 선택이다.

```typescript
// src/types/blog.ts
export type RaceFact = {
  label: string;   // '대회일'
  value: string;   // '12월 6일'
  sub?: string;    // '일 · 07:30'
};

export type RaceHighlight = {
  badge: string;   // '3×'  — 숫자·기간·범주. 순번(01/02/03) 금지
  title: string;   // '오르막이 세 번 온다'
  desc: string;    // 한두 문장
};

export type RaceMeta = {
  /** 화면용 제목 — 검색용 `title` 과 별개. 40자 이하 */
  displayTitle: string;          // '국내 첫 트리플 브릿지 풀코스 — 부산브릿지마라톤'
  /** 화면용 부제 */
  displaySubtitle?: string;      // '광안대교·부산항대교·남항대교를 하루에 다 건넌다'
  /** 대회 당일 (KST, ISO date) */
  raceDate: string;              // '2026-12-06'
  /** 접수 시작·마감 (분 단위까지, KST) — 미정이면 생략 */
  registrationStart?: string;    // '2026-08-24T10:00'
  registrationEnd?: string;
  /** 접수처 표기 — 배지·행동 스트립에서 씀 */
  registrationVia?: string;      // 'YES24 티켓'
  /** 지금 해야 할 행동 하나 */
  action?: { what: string; how: string };
  /** 핵심 카드 4~6장 */
  facts: RaceFact[];
  /** 이 대회만의 것 2~4개 */
  highlights: RaceHighlight[];
  /** 마라톤 DB 연결 (있으면) */
  marathonId?: string;
};
```

`BlogPost` 에 `raceMeta?: RaceMeta` 를 옵셔널로 추가한다.

### 왜 `status` 필드를 두지 않는가

[[marathon-data-verification]]과 [[marathon-discovery-2026-08]]의 결론이 같다 — **날짜가 수동 status를 이긴다.** 손으로 적은 상태값은 반드시 낡는다(3-4절이 그 증거다). 상태는 `raceDate`·`registrationStart`·`registrationEnd` 에서 **파생**한다.

```
registrationStart 미정          → 'tbd'      (발표 대기)
now < registrationStart         → 'upcoming' (D-n)
registrationStart ≤ now ≤ End   → 'open'     (접수중)
now > registrationEnd           → 'closed'   (접수 마감)
now > raceDate                  → 'past'     (종료)
```

### D-day는 클라이언트에서 계산한다

이 사이트는 SSG다. 빌드 시점에 D-day를 굳히면 **다음 배포까지 낡는다** — 3-4절의 D-12가 정확히 그 사고다. 따라서 `RaceStatusBadge` 는 작은 클라이언트 컴포넌트로 만들어 **브라우저의 현재 시각으로** 계산한다.

- 서버는 `raceMeta` 의 날짜 **문자열만** prop으로 넘긴다
- ⚠️ [[perf-network-round-2026-07]]의 함정: `'use client'` 컴포넌트가 모듈 스코프에서 데이터 getter를 부르면 풀데이터가 클라 번들에 실린다. 이 컴포넌트는 **getter를 부르지 않고 prop만 받는다**
- 서버 렌더 시점에는 날짜 텍스트(`8월 24일(월) 10:00`)를 보여주고, hydration 후 D-day를 덧붙인다 — JS가 없어도 정보는 남는다

## 6. 컴포넌트 설계

전부 `src/components/blog/race/` 아래 둔다. 각각 하나의 일만 한다.

| 컴포넌트 | 입력 | 하는 일 |
|---|---|---|
| `RaceStatusBadge` | 날짜 문자열들 | 상태 파생 + D-day. **유일한 클라이언트 컴포넌트** |
| `RaceActionStrip` | `action`, 날짜 | "지금 할 행동 하나" 블록 |
| `RaceFactGrid` | `facts[]` | 핵심 카드 4~6장 그리드 |
| `RaceHighlights` | `highlights[]` | 차별점 블록 |

상태 파생 로직은 컴포넌트가 아니라 `src/lib/blog/race-status.ts` 의 순수 함수로 둔다 — 인자로 `now` 를 받아 테스트가 시각에 의존하지 않게 한다.

```typescript
export function deriveRaceStatus(meta: RaceMeta, now: Date): RaceStatus
```

렌더 순서는 `blog/[slug]/page.tsx` 에서 `raceMeta` 가 있을 때만:

```
배지 → displayTitle → displaySubtitle → 행동 스트립 → 핵심 카드
  → 차별점 블록 → [본문 content] → 신발 브릿지 → FAQ
```

**차별점 블록까지가 고정 골격이다.** 데이터(`highlights`)로 두고 컴포넌트가 고정 위치에 렌더한다 — 위치를 글마다 다르게 두면 표준화라는 목적 자체가 무너지고, 3-5절의 편차가 그대로 재발한다.

**전체 요강표만 본문 HTML 안에** 둔다(맨 아래). 대회마다 항목이 다르고(자격제 여부·부문 구성) 표 구조를 데이터로 강제하면 오히려 표현이 좁아지기 때문이다.

## 7. validate 강제 규칙

`scripts/validate.js` 에 검사를 추가한다. **`raceMeta` 가 있는 글에만** 적용되므로 기존 글은 걸리지 않는다.

| # | 검사 | 수준 | 이유 |
|---|---|---|---|
| 1 | `facts` 4~6개 | **에러** | 3개면 그리드가 빈다, 7개면 스캔이 안 된다 |
| 2 | `highlights` 2~4개 | **에러** | 1개면 "이 대회만의 것"이 성립 안 함 |
| 3 | 본문에 `class="tldr"` 없을 것 | **에러** | 3줄 요약 폐지가 이 설계의 핵심 |
| 4 | slug에 `20\d\d` 없을 것 | **에러** | 8절 |
| 5 | 고유 `/shoes/` 링크 3개 미만 | **경고** | 3개 이상은 정당한 큐레이션일 수 있다(3-2절) |
| 6 | `raceDate` 가 파싱 가능한 날짜 | **에러** | 상태 파생의 전제 |
| 7 | `registrationEnd` ≥ `registrationStart` | **에러** | 순서가 뒤집히면 상태가 영구 `closed` |
| 8 | `displayTitle` 40자 이하 | **에러** | 이 길이를 넘으면 414px에서 3줄이 된다 — 고치려던 바로 그 증상 |
| 9 | `displayTitle` 이 `title` 과 동일하지 않을 것 | **경고** | 같으면 별도 필드를 둔 의미가 없다(검색 제목을 복사한 것) |

3·4번을 에러로 두는 이유는 **경고는 무시되기 때문**이다. 기존 글이 안 걸리므로 에러로 둬도 커밋이 막히지 않는다.

## 8. slug 규칙

신규 대회 글의 slug에서 **연도를 뺀다.**

- `busan-bridge-marathon-2027` ❌ → `busan-bridge-marathon` ✅
- **제목·본문의 연도는 그대로 둔다.** 검색어 `2027 부산마라톤` 을 받아야 한다. 빼는 것은 URL뿐이다
- 내년 같은 대회가 오면 같은 글을 갱신하고, 지난 회차는 본문 "지난 대회" 섹션으로 내린다

**기존 65편은 바꾸지 않는다.** slug 변경은 순위 초기화 위험이 있고, 그 이득이 위험보다 크다는 근거가 없다.

**근거**: 대회 글 72편 중 65편(90%)이 slug에 연도를 박았는데, 같은 대회의 연도 다른 글은 **0건**이다. 갱신 사이클을 한 번도 안 돌았다는 뜻이고, 내년 봄에 "새 글을 쓰면 권위 0에서 시작 / 기존 글을 갱신하면 URL이 거짓말" 갈림길이 온다. 90%가 연도를 박아둔 탓에 후자를 고를 수 없게 되어 있다.

## 9. 카드뉴스 — 이미지를 만들지 않는 결정

운영자 요청은 "카드뉴스처럼 이미지나 표로 보기 좋게"였다. **표·HTML 카드로 구현하고 이미지는 만들지 않는다.**

| | 이미지 카드 | HTML 카드 (채택) |
|---|---|---|
| 갱신 | 글을 고쳐도 안 따라옴 (**실증: 썸네일 6 vs 제목 7**) | 데이터가 곧 화면 |
| 검색 | 이미지 안 텍스트는 안 잡힘 | 본문 텍스트로 색인 |
| 반응형 | 고정 비율 | 폭에 맞춰 재배치 |
| 다크모드 | 한 벌 더 필요 | 토큰으로 자동 |

대회 정보는 접수 상태·마감일이 계속 바뀐다. **바뀌는 정보를 이미지에 굽지 않는다**는 것이 이 결정의 한 줄 요약이다.

**예외 — 코스 지도.** 텍스트로 대체 불가능한 유일한 이미지다. 다만 대회 공식 코스맵은 저작권 확인이 필요하므로 **이번 범위에서 제외**하고 별도 판단한다.

## 10. 신발 브릿지 조건 완화

`page.tsx:266-268` 의 이진 조건을 임계값으로 바꾼다.

```
현재:  신발 링크가 하나라도 있으면 → 브릿지 0장
변경:  고유 신발 링크 3개 미만이면 → 브릿지 렌더
```

- **임계값 3의 근거**: 3-2절
- **영향**: 브릿지 켜진 글 34편 → **48편** (대상 72편의 47% → 67%)
- **중복 처리**: 본문에 이미 링크된 신발은 카드에서 제외한다(`excludeSlugs` prop). 부산브릿지 글은 본문에 님버스 28이 있으므로, 없으면 카드에 님버스가 또 나온다
- **롤백**: 조건식 한 줄. slug·본문 무변경이라 순위 영향 없음

이 변경은 `raceMeta` 유무와 **무관하게 72편 전체에 적용**된다. 이 설계에서 기존 글에 영향을 주는 유일한 항목이다.

## 12. 측정과 판정

**정직하게: 지금 이 설계의 효과를 깨끗하게 판정할 수단이 없다.**

- GSC·GA 서비스 계정 키가 없다(2절 한계). 운영자가 경로를 주면 해소된다
- AdSense는 페이지별 RPM을 주지 않는다
- `npm run gsc:pages` 는 이번에 package.json에 등록했으나(스크립트 파일만 있고 npm script가 없었다) **키가 없어 아직 한 번도 실행되지 않았다**

따라서 판정은 두 층으로 나눈다.

**즉시 검증 가능 (빌드 산출물)**
- 브릿지 렌더 편수 34 → 48
- `raceMeta` 보유 글에서 `class="tldr"` 0건
- 신규 글 slug에 연도 0건

**4주 뒤 간접 판정 (키 확보 시)**
- 신규 대회 글의 노출 발생 여부 — 기준선은 0
- 기존 대회 글 대비 체류·순위 비교

**실패로 판정할 조건**: 새 표준으로 쓴 대회 글 3편이 4주 뒤에도 노출 0이면, 문제는 구성이 아니라 **대회 글 자체가 검색에서 밀리는 것**이다. 그때는 구성을 더 만지지 말고 [[content-brand-lineup-opportunity]]처럼 각도를 바꾼다.
