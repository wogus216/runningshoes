# 러닝 후 회복 · 트레일 입문 — 콘텐츠 축 설계

- 작성일: 2026-08-18
- 상태: 설계 승인 대기
- 범위: 콘텐츠 축 2개 신설 + 리커버리 슈즈 데이터 타입 신설

---

## 1. 배경

운영자 요청: **트레일 강화 + 러닝 후 웰니스 확장**.

착수 시점의 가설은 "웰니스 콘텐츠를 늘린다"였다. 실측 결과 그 가설은 **절반만 맞았다** — 수요는 분명히 있으나, 우리가 이미 쓴 웰니스 글들은 그 수요를 잡지 못하고 있었다. 원인은 분량이 아니라 **각도**였다. 이 문서는 각도를 바꾸는 설계다.

---

## 2. 측정 사양

수치를 인용하기 전에 다음을 고정한다.

| 항목 | 값 |
|---|---|
| 분석 단위 | 페이지(블로그 글) · 검색어 · 커뮤니티 스레드 |
| 모집단 | allrunabout.com 전체 / DC인사이드 러닝 마이너 갤러리 |
| 데이터 시점 | GA4 최근 90일 · GSC 2026-07-18~08-15(28일) · DC 2026-08-18 조회 |
| 집계 | 조회수·클릭 합계, TOP N 절단 |
| 포함·제외 | 블로그 글 전체 포함. `/shoes`·`/marathon` 등 비블로그 경로는 비교군으로만 사용 |

**한계 (반드시 함께 읽을 것)**

- `npm run ga`는 TOP30, `npm run gsc`는 상위 12페이지만 출력한다. 따라서 개별 웰니스 글의 **정확한 조회수·클릭은 불명**이다. 확정 가능한 것은 "TOP 진입 실패"까지다.
- DC 조회수는 스레드 노출량이지 검색 수요가 아니다. **관심의 방향을 읽는 용도**로만 쓰고, 크기 비교에는 쓰지 않는다.
- 네이버 검색량은 확인하지 못했다(API 없음). 한국 유입의 63%가 네이버 경유임을 감안하면 이 공백은 실제 리스크다. → 9절 열린 질문.

## 3. 실측 근거

### 3-1. 웰니스 글은 현재 유입을 만들지 못하고 있다

- GA4 TOP30(90일): 웰니스·부상 글 **0편**
- GSC 상위 페이지 12개: **0편** (= 각각 28일 클릭 41 미만)
- GSC 상위 검색어 15개: 웰니스 쿼리 **0개**. 순위 공략 후보 12개 중 `폭염 러닝`(노출 135·클릭 10·CTR 7.4%) 하나뿐

부상 가이드 7편은 2026-06-22~07-08 발행으로 41~57일이 지났다. 색인 미성숙만으로 설명하기 어렵다.

대조군: GSC 상위 페이지 12개 중 **9개가 신발 후기·비교**다. 우리가 이기는 레인은 일관되게 제품 비교다.

### 3-2. 그러나 수요 자체는 갈증 상태로 존재한다

DC 러닝 갤러리 검색 결과(2026-08-18):

|---|---|
| 리커버리 러닝 이거 효과있는거 맞음? | 521 |
| 러닝후 피로를 빠르게 회복하는 방법 잇어??? | 366 |
| 회복런 하는게 도움됨??? | 344 |
| 레이싱데이 담날 리커버리용 신발 ㅊㅊ받습니다 | 159 |

**질문형 스레드가 일상 인증글보다 조회수가 높다.** 답이 정리된 곳이 없어 반복해서 묻고 있다는 신호다. 네 번째는 리커버리 슈즈 추천 요청의 원문이다.

외부 공급 현황: GQ코리아 "리커버리 슈즈 추천 9", 무신사 상품 후기, 브런치·런마일·모스포츠·On 공식 등. **매거진과 쇼핑몰은 있고, 데이터 검증형은 없다.**

### 3-3. 트레일은 DB가 아니라 진입 계단이 없다

현재 트레일 자산:

| 신발 DB | 13종 (6개 카테고리 중 최하위 타이) |

우리 자산은 **이미 트레일을 하는 사람용**으로 9:1 기울어 있다. 신발을 더 추가해도 이 갈증은 안 풀린다. **신발 DB 보강은 후순위**다.

## 4. 문제 정의

두 축 모두 같은 병이다.

> **우리는 "이미 그것을 하는 사람"을 위한 글을 썼고, 사람들은 "그것을 시작할지 고민하는 단계"에서 묻고 있다.**

부상 글 7편이 안 먹힌 이유도 같다. 아플 때만 읽는 글이고, 그 순간의 경쟁 상대는 병원·의료 콘텐츠다. 반면 "러닝 후 뭘 해야 하나"는 **매주 반복되는 질문**이다.

## 5. 설계 — 축 1: 트레일 입문 계단

### 원칙

**실수요 질문을 그대로 제목으로 받고, 기존 신발 비교 9편을 착지점으로 쓴다.**

기존 입문 글 `trail-running-appeal-beginner-guide-2026`("왜 빠질까")은 감성 축이다. 새 글은 **의사결정 축**으로 차별화한다 — 할지 말지, 뭘 사야 하는지, 내가 되는지.

### 콘텐츠 각도

| # | 각도 | 받는 실수요 | 착지점 |
|---|---|---|---|
| T1 | 로드 러너가 처음 산에 갈 때 실제로 필요한 것 — 장비 최소 세트·첫 코스·체력 조건 | "해본 사람 있나" "뭐가 다른가" "반팔 추천" | `2026-best-trail-running-shoes`, 대회 글 4편 |
| T2 | 트레일화 정말 필요한가 — 흙길엔 로드화로 충분한가 | "흙바닥에서 트레일화가 더 나은가요"(원문) | 신발 비교 9편 전체 |
| T3 | 체중·무릎 걱정되는데 산에 가도 되나 | "체중 좀 있으면 ㅈ되겠지??" | 쿠션 트레일화(히에로 v9 등), 부상 글 7편 **회수** |

T3은 **부상 글 7편을 살려내는 경로**다. 지금 부상 글은 들어오는 문이 없다. 트레일 입문 글이 그 문이 된다.

### 신발 DB 보강 (후순위)

13종 → 목표 미정. 진행한다면 국내 유통 확인이 선행이다(살로몬 추가 때 researcher 초안 3종이 한국 미판매였던 전례). 이 문서의 범위는 **입문 계단까지**로 하고, DB 보강은 별도 사이클로 뺀다.

## 6. 설계 — 축 2: 러닝 후 회복

### 콘텐츠 각도

| # | 각도 | 받는 실수요 | 비고 |
|---|---|---|---|
| R1 | 레이싱 다음날 뭘 신나 — 리커버리 슈즈 비교 | "레이싱데이 담날 리커버리용 신발 ㅊㅊ"(원문) | 제품 비교. 6절 데이터 필요 |
| R2 | 회복런 진짜 효과 있나 — 근거와 실제 페이스 | 조회 521·344의 반복 질문 | 근거 검증형. 우리 스타일과 상성 |
| R3 | 러닝 후 30분 — 뭘 먹고 뭘 하나 | "피로를 빠르게 회복하는 방법"(조회 366) | 젤 13종 페이지로 착지 |

R2는 근거가 엇갈리는 주제다(사우나·냉수욕은 효과가 주관적 피로감에 그친다는 보고 존재). **엇갈린다는 사실 자체를 쓰는 것**이 우리 차별점이다. 단정하지 않는다.

### E-E-A-T 경계

- 의학적 진단·치료 주장 금지. 기존 부상 글의 톤(원인·자가진단·"신발의 진짜 역할")을 따른다
- 1차 원문 확인 없이 효과를 단정하지 않는다 → [[feedback-verify-before-publish]]
- 리커버리 슈즈 성능은 **실측이 아니라 구조 설명**으로 쓴다. 우리는 랩 테스트를 하지 않는다

## 7. 리커버리 슈즈 데이터 구조

### 결정: `gels` 방식의 별도 데이터 (운영자 승인)

`Shoe` 타입 재사용은 부적절하다. `biomechanics`(스택·드롭·전이), `injuryPrevention`(부상별 등급), `specs.responsiveness`·`durability`(km) 등이 **전부 러닝 전제**이며 슬리퍼에는 무의미하다. 빈칸으로 채우면 렌더 표면이 깨지고 `validate.js`가 오작동한다.

### 파일 배치 (gels 패턴 그대로)

```
src/types/recovery.ts                 # 타입 정의
src/lib/data/recovery/
  ├── index.ts                        # getRecoveryShoes() 등 조립
  ├── slides.ts                       # 슬라이드/샌들
  └── shoes.ts                        # 발을 감싸는 형태(뮬·클로그)
src/app/(main)/recovery/page.tsx      # 목록
src/app/(detail)/recovery/[slug]/page.tsx  # 상세
```

### 타입 초안

러닝화 필드를 끌어오지 않고, **회복 슈즈가 실제로 갈리는 지점**만 담는다.

```typescript
export type RecoveryShoeForm = 'slide' | 'mule' | 'clog' | 'sandal';
export type CushionFeel = 'soft' | 'balanced' | 'firm';

export interface RecoveryShoe {
  id: string;
  slug: string;
  brand: string;
  name: string;
  form: RecoveryShoeForm;
  price: number;              // 한국 공식가 (원)
  description: string;

  fit: {
    archSupport: 1 | 2 | 3 | 4 | 5;   // 아치 지지 정도
    cushionFeel: CushionFeel;
    rocker: boolean;                   // 로커 형상 유무 (걷기 편의)
    widthNote: string;                 // 한국인 발볼 관점 메모
  };

  usage: {
    indoorOutdoor: '실내' | '실외' | '겸용';
    waterFriendly: boolean;            // 비/샤워장 사용
    walkableDistance: string;          // "단거리 이동" / "일상 보행 가능"
    bestFor: string[];                 // ["대회 직후", "장거리 다음날"]
    avoidIf: string[];                 // ["발등 마찰 예민", "장시간 보행"]
  };

  editorNote: string;                  // 구조 기반 해석 (실측 주장 금지)
  officialUrl?: string;
  image?: string;
}
```

**의도적으로 넣지 않은 것**: 무게 점수화, 에너지 리턴, 내구 km, 부상별 등급, `reviews`. 근거 없는 숫자를 만들지 않기 위해서다.

### SEO 기대치 (중요)

`/gels`는 검색 유입이 사실상 죽은 레인이다([[pseo-vs-is-the-working-lane]]). `/recovery`도 같을 것으로 **가정한다**. 따라서:

- 라우트는 **블로그 글의 착지점**으로 만든다. 라우트 자체의 검색 유입은 기대하지 않는다
- 유입은 R1 블로그 글이 만든다
- `/recovery` 목록 페이지에 광고를 넣지 않는다(인덱스 페이지 광고는 하지 말 것 목록)

## 8. 내부링크 설계

두 축을 따로 두지 않고 **하나의 회로**로 잇는다.

```
[T3 체중·무릎 걱정]  ─→  부상 글 7편 (현재 고립)
        │
        └─→ [T1 첫 산행 장비] ─→ 트레일 신발 비교 9편 ─→ /shoes/*
                                        │
[R1 레이싱 다음날 뭘 신나] ─→ /recovery/*  ←┘ (대회 직후 회복 문맥)
        │
        └─→ [R3 러닝 후 30분] ─→ /gels/* (보급·회복 영양)
                │
                └─→ [R2 회복런 근거] ─→ running-warmup-cooldown-guide-2026
```

핵심은 **고립 자산 회수**다. 부상 글 7편과 `/gels` 13종은 지금 들어오는 문이 없다. 신규 글이 그 문이 된다.

## 9. 비목표 (YAGNI)

- 리커버리 슈즈 **비교 기능**(`/compare` 편입) — 만들지 않는다. 항목 수가 적고 축이 단순하다
- 마사지건·폼롤러 **제품 DB** — 신발 사이트 정체성에서 멀다. 필요하면 블로그 본문 서술로 처리
- 트레일 **신발 DB 대량 보강** — 별도 사이클
- `/best/recovery` 같은 pSEO 매트릭스 편입 — `/best`는 죽은 레인
- 수면·사우나 **단독 글** — 근거가 엇갈려 단독으로는 위험. R2 안에서 다룬다

## 10. 검증

| 대상 | 방법 |
|---|---|
| 데이터 무결성 | `npm run validate` 에러 0 |
| 빌드 | `npm run build` 통과 |
| 내부링크 | 발행 전 본문 slug를 grep 1회로 일괄 확인 → [[feedback_blog_internal_links]] |
| 주제 중복 | 발행 전 기존 15편 트레일 글과 각도 대조 → [[feedback_blog_topic_dedup]] |
| 성과 | 발행 4주 후 `npm run gsc`로 신규 slug의 노출·순위 확인. **TOP12 진입 여부가 아니라 노출 발생 여부**를 1차 기준으로 본다 |

성과 판정 기준을 미리 못박는다: **4주 후 노출 0이면 각도 실패로 간주**하고 축을 접는다. 부상 글 7편의 실패를 반복하지 않기 위한 장치다.

## 11. 구현 분해

이 설계는 **단일 구현 계획으로 묶기엔 크다**(콘텐츠 6편 + 타입 신설 + 라우트 2개). 두 사이클로 나눈다.

| 사이클 | 범위 | 근거 |
|---|---|---|
| **A** | 트레일 입문 3편(T1~T3) | 코드 변경 0. 기존 자산만으로 성립하므로 가장 싸고 빠르다. 각도 가설을 먼저 검증한다 |
| **B** | 리커버리 데이터 + 라우트 + 회복 3편(R1~R3) | 타입·라우트 신설이 걸려 비용이 크다. A의 4주 성과를 보고 착수 여부를 판단한다 |

A를 먼저 하는 이유는 **각도 가설(질문형 제목 + 고립 자산 회수)이 맞는지를 코드 비용 0으로 검증**할 수 있어서다. 가설이 틀리면 B의 타입·라우트 작업이 통째로 낭비된다.

## 12. 열린 질문 — 착수 전 운영자 확인 필요

1. **트레일 신발 DB 보강을 이 범위에서 뺀 것** — 원 요청은 "트레일 강화"였는데, 실측상 병목이 DB가 아니라 진입 계단이라 판단해 **별도 사이클로 미뤘다.** 13종은 6개 카테고리 중 최하위 타이라 보강 자체는 언젠가 필요하다. 이 축소가 의도와 맞는지 확인이 필요하다
2. **네이버 검색량 미확인** — 유입의 63%가 네이버 경유인데 네이버 수요를 직접 못 봤다. 이 설계의 근거는 GSC(구글)와 DC(커뮤니티)뿐이다. 발행 전 네이버 자동완성·연관검색어로 보완할지?
3. **편수·발행 순서** — 운영자가 "규모 미정"으로 남김. 사이클 A의 3편을 한 번에 낼지, 1편씩 낼지
4. **리커버리 슈즈 초기 수록 대상** — 호카 오라 리커버리 슬라이드 3·뮬이 국내 화제의 중심. 몇 종으로 시작할지 미정
5. **이미지** — `/recovery` 상세에 이미지가 필요한지. 신발 DB에선 이미지 없는 항목이 `/best`에서 제외되는 함정이 있었다(`hasMinimumData`). `/recovery`는 매트릭스 밖이라 무관하지만 상세 품질에는 영향
