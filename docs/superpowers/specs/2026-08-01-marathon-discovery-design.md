# 마라톤 대회 탐색 개선 설계

작성일 2026-08-01 · 대상 `/marathon` 목록 · 상태 승인됨

---

## 1. 문제

오늘(2026-08-01) 기준 `/marathon` 첫 화면의 카드 3개가 전부 **대회종료**다(3/1, 3/1, 3/7).
100개 중 48개(48%)가 이미 지난 대회인데 정렬이 날짜 오름차순 하나뿐이라 끝난 대회가 먼저 나온다.
지금 신청 가능한 32개를 보려면 필터를 직접 만져야 한다.

GA 실측에서 **대회 접수 발표일이 `/marathon/[id]` 수익 스파이크**로 확인돼 있다
([[project_revenue_bottleneck]]). 목록이 "지금 열린 대회"를 못 보여주는 건 그 수요를 그대로 흘리는 것이다.

### 데이터 실측 (2026-08-01)

| 항목 | 값 |
|---|---|
| 전체 | 100 (2026-03-01 ~ 2026-12-06) |
| 지난 대회 (`date < 오늘`) | **48** |
| 지금 접수중 | 32 |
| 접수예정 | 8 |
| 마감(대회는 남음) | 12 |
| 지역 | 서울 26 · 경북 11 · 경기 11 · 인천 8 · 전남 6 · 강원 6 · 나머지 한 자릿수 |
| 거리 | 10K 84 · 하프 69 · 5K 59 · 풀 28 · 울트라 12 · 트레일 7 |

`status` 와 `date` 는 현재 모순 0건이다(접수중인데 과거 0 · 대회종료인데 미래 0). 관리가 잘 되고 있다.

### 3.1 밴드가 정렬을 대체한다

정렬 옵션(`date-asc` / `date-desc` / `name-asc`)은 **없앤다.** 밴드 자체가 시의성 정렬이고,
밴드 안에서는 항상 날짜 오름차순이다. 사용자가 정렬을 고를 이유가 사라진다.

기본 펼침은 앞 두 밴드(접수중 · 곧 열림)뿐이다. 뒤 두 밴드(접수 마감 · 지난 대회)는
`<details>` 로 접히되 **안쪽에 해당 밴드의 전체 행을 담는다** — 접힌 밴드는 점진 확장을 쓰지 않는다.
홈 인덱스가 122행을 `<details>` 로 보존한 것과 같은 이유로, 검색 유입과 내부 링크를 잃지 않는다.

각 밴드는 기본 **12행**을 노출하고 `N개 더 보기` 로 **12행씩** 점진 확장한다.
데스크톱·모바일 모두 12다 — 홈 인덱스(16/12)와 달리 밴드가 넷으로 쪼개져 있어
데스크톱에서 16씩 열면 첫 화면이 한 밴드로 차 버린다.
남은 수가 12 이하면 버튼 문구는 `전체 N개 보기` 다.

### 3.2 사이드바를 없애고 가로 칩으로

행 목록 왼쪽에 사이드바가 붙으면 행 폭이 좁아져 `날짜 · 이름 · 권역 · 거리 · 상태` 가
한 줄에 들어가지 않는다. 필터는 목록 위 가로 칩으로 올린다.

축은 **권역 · 거리 · 메이저** 셋이다. 접수상태 필터는 밴드와 중복이라 제거하고,
월별 필터도 뺀다 — 밴드 안이 날짜순이라 스크롤로 충분하고, 칩이 6+6+1+12 로 불어나면
필터가 목록보다 커진다.

권역 그룹(수도권/강원/충청/전라/경상/제주)은 `marathon-filter-panel.tsx` 에 **이미 구현돼 있다.**
그대로 가져다 쓴다.

### 3.3 행 구조

```
날짜(요일) · 대회명 · 권역 · 거리 목록 · 상태
```

- 날짜는 mono + `tabular-nums`, 나머지 한글은 본문 서체(스펙 §3 — mono 는 수치·라벨 전용)
- 상태 칸은 `registrationEnd` 가 있으면 `D-12 마감`, 없으면 `접수중` 배지
- 메이저 대회는 이름 옆에 작은 표식
- 행 전체가 `/marathon/[id]` 로 가는 링크(stretched-link)

모바일은 2행으로 접는다 — 1행 `날짜 · 대회명`, 2행 `권역 · 거리 · 상태`.

## 4. 밴드 판정 규칙

| 밴드 | 조건 | 근거 |
|---|---|---|
| 지난 대회 | `date < 오늘` | **자동 · 100% 신뢰** |
| 접수 마감 | `registrationEnd < 오늘` **또는** `status === '마감'` | 날짜 있으면 자동 |
| 곧 열림 | `registrationStart > 오늘` **또는** `status === '접수예정'` | 〃 |
| 지금 접수중 | 위 셋에 해당하지 않음 | 수동 `status` 의존 |

**날짜가 수동 `status` 를 이긴다.** `registrationEnd` 가 지났는데 `status` 가 아직 `접수중` 이면
마감 밴드로 내린다 — 자동 판정이 항상 더 최신이다.

판정 순서는 위 표의 위에서 아래다(지난 대회를 먼저 걸러낸다).

## 5. 데이터 모델 변경

```ts
export interface MarathonEvent {
  // ... 기존 필드
  /** 접수 시작일 'YYYY-MM-DD'. 있으면 밴드 판정과 D-day 표기에 쓴다 */
  registrationStart?: string;
  /** 접수 마감일 'YYYY-MM-DD' */
  registrationEnd?: string;
  /** status 를 마지막으로 확인한 날. 대회 상세에만 노출한다 */
  lastVerified?: string;
}
```

**셋 다 선택 필드다. 100개를 지금 채우지 않는다.**
채워진 대회만 `D-12 마감` 같은 자동 표기가 붙고, 안 채워진 대회는 지금처럼 `접수중` 배지만 단다.
새로 들어오는 대회부터 채우면 자동화 비율이 시간이 갈수록 올라간다.

`npm run validate` 에 규칙 하나를 더한다 — **`registrationEnd` 가 `date` 보다 늦으면 에러.**
접수 마감이 대회일보다 뒤일 수는 없다.

### 정직성 표기

접수중 밴드 아래 한 줄을 고정한다.

> 접수 상태는 공식 발표를 수동 확인한 값입니다. 신청 전 공식 페이지에서 다시 확인하세요.

개별 `lastVerified` 는 **목록이 아니라 대회 상세**에 둔다. 목록 헤더에 "8/1 확인" 이라고 쓰면
6월에 확인한 대회까지 8/1 에 확인한 것처럼 읽힌다.

## 6. 이상 거리값

데이터에 `11K` · `6K` · `12K` 가 각 1건씩 있는데 `EVENT_DISTANCES` 에 없는 값이다.
타입은 `EventDistance` 인데 데이터가 벗어나 있어 **그 대회들은 거리 필터에 영영 안 잡힌다.**

**표기는 원문 그대로 두고 필터만 근접 표준에 매핑한다.**

| 실제 값 | 필터 매핑 |
|---|---|
| `11K` · `12K` | `10K` |
| `6K` | `5K` |

칩을 9개로 늘리지 않는 이유는 변별력이 없어서다(각 1건). 반대로 "10K 대회 보여줘" 했을 때
11K 대회가 안 나오는 게 더 이상하다. 행에는 `11K` 로 정직하게 표기한다.

## 8. 리스크

| 리스크 | 대응 |
|---|---|
| `status` 가 낡아 "접수중"이 거짓이 됨 | 접수기간 필드로 자동 판정 우선 + 고정 문구로 재확인 유도 |
| 지난 대회를 접어 검색 유입 손실 | 마크업에 전부 유지(`<details>`), 링크 100개 보존을 검증 항목으로 |
| 월별 필터 제거로 계획형 탐색 약화 | 밴드 안이 날짜순이고 12행 단위 점진 확장이라 8월→9월 흐름이 스크롤로 읽힌다. 배포 후 필요하면 되살린다 |
| 필터 축 축소로 특정 지역 탐색 불편 | 권역 6개는 기존 그룹 그대로. 시·도 단위가 필요하다는 피드백이 오면 2단계로 |

## 9. 이 스펙이 다루지 않는 것

- **블로그 탐색** — 같은 "찾을 수가 없다" 문제지만 축(주제·신발·상황)과 시의성이 달라 별도 스펙
- **대회 상세 레이아웃** — 이번엔 `lastVerified` 표기만 추가한다
- **접수 기간 100개 백필** — 필드만 열고, 채우는 건 운영 작업으로 남긴다
