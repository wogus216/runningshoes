# 블로그 관련글 관련도 설계

**작성일**: 2026-08-02
**범위**: 블로그 전면 개편의 **서브프로젝트 2/3** 중 첫 조각 — 글 페이지 하단 관련글 모듈

## 1. 문제

블로그 221편 중 **63편(29%)이 28일간 조회 0**이고, 세션당 페이지 수가 **1.95**다.
검색으로 글 하나에 떨어진 사람이 그 글만 보고 나간다.

원인을 추적하니 **관련글 모듈이 사실상 고장나 있었다.**

### 1.1 현재 알고리즘

`src/lib/data/blog/index.ts`의 `getRelatedPosts`:

```ts
blogPosts
  .filter((post) => post.slug !== slug)
  .filter((post) =>
    post.category === currentPost.category ||
    post.tags.some((tag) => currentPost.tags.includes(tag))
  )
  .sort((a, b) => new Date(b.publishedAt).getTime() - new Date(a.publishedAt).getTime())
  .slice(0, limit);
```

**결함은 2단계에 있다.** `같은 카테고리 OR 태그 공유`로 거른 뒤 **관련도를 버리고 날짜순으로만**
정렬한다. `review`·`guide`가 각각 75편이라 "같은 카테고리" 하나로 74편이 통과하고, 거기서
최신 3개를 뽑으면 **같은 카테고리의 모든 글이 같은 3편을 가리킨다.** 태그 일치와 카테고리
일치의 가중치가 동일하다는 것도 문제다 — 정밀한 신호가 뭉툭한 신호에 묻힌다.

### 1.2 실측

221편 전체에 대해 `getRelatedPosts(slug, 3)`를 돌려 집계했다.

| 항목 | 값 |
|---|---:|
| 관련글로 **한 번이라도** 노출되는 글 | **27편 / 221편 (12%)** |
| 한 번도 노출되지 않는 글 | **194편** |
| 상위 10편이 차지하는 추천 슬롯 | **96%** (634/663) |
| 최다 노출 글 | 77회 |

`running-shoe-500km-replacement-myth-2026` 한 편이 77회, 상위 5편이 각각 75회 안팎 노출된다.
**194편은 사이트 어디에서도 추천되지 않는다.** 검색에 안 걸리면 도달 경로가 없다.

### 1.3 왜 이게 두 목표의 공통 원인인가

- **두 번째 글을 안 읽는다** — 추천이 읽던 글과 무관한 최신글이라 누를 이유가 없다
- **63편이 조회 0이다** — 194편이 추천 대상에서 구조적으로 배제돼 있다

> ⚠️ 이 진단은 앞서 확인한 "내부 링크 → 순위 가설 반증"과 모순되지 않는다.
> 본문에 하드코딩된 링크 수는 트래픽과 상관이 없었다(링크 41건에 조회 3, 링크 0건에 클릭 127).
> 관련글 모듈은 **모든 글 하단에 자동으로 붙는 노출면**이라 성격이 다르다.

## 2. 목표

1. 글을 읽은 사람이 **두 번째 글로 갈 길**을 만든다
2. 추천에서 배제된 **194편이 노출되게** 한다

**목표가 아닌 것**: 검색 유입 증가. 구글·네이버 순위는 이 작업으로 안 움직인다.
이미 들어온 사람의 회유가 전부다.

## 3. 설계

### 3.1 점수

```
score(현재글, 후보글) =
    Σ IDF(공유 태그)                  ← 주력
  + Σ IDF(공유 /shoes/ 링크)           ← 이 사이트만의 신호
  + 0.3 × (같은 카테고리 ? 1 : 0)      ← 안전망

IDF(t) = log(221 / (1 + t를 쓴 글 수))

정렬: score 내림차순 → 동점이면 publishedAt 내림차순 → 상위 6개
```

**왜 IDF인가.** 태그 1144개 중 **900개(79%)가 딱 한 번만** 쓰였고, 20회 이상 쓰인 태그는
**0개**다. 통제된 분류체계가 아니라 자유 텍스트다. 그런데 바로 그래서 **공유될 때 정보량이
크다** — 두 글이 희귀 태그를 공유하면 우연이 아니다. 흔한 태그(`러닝화 비교` 19회)와 희귀
태그를 같은 무게로 세면 그 신호가 사라진다.

**왜 `/shoes/` 링크인가.** 본문이 같은 신발을 링크하는 두 글은 태그와 무관하게 실제로 관련
있다. 이 신호를 뽑는 코드는 이미 있다(`buildShoeLinkIndex`가 신발 상세용으로 쓴다).

**왜 카테고리 가중치가 0.3인가.** 카테고리는 74편을 한꺼번에 통과시키는 뭉툭한 신호라
주력이 될 수 없다. 다만 태그도 신발도 안 겹치는 글에 **추천 0이 나오는 걸 막는 안전망**으로는
필요하다(§3.2 표 참조).

### 3.2 근거 — 프로토타입 실측

221편 전체에 대해 변형별로 돌린 결과다.

| 방식 | 노출 편수 | 상위10 점유 | 추천 0인 글 |
|---|---:|---:|---:|
| **현재 (카테고리 필터 + 날짜순)** | 27 (12%) | **96%** | 0 |
| 태그만 (IDF) | 202 (91%) | 15% | 2편 |
| 신발 링크만 (IDF) | 124 (56%) | 29% | **52편** |
| 태그 + 신발 | 198 (90%) | 16% | 1편 |
| **태그 + 신발 + 카테고리 0.3 (채택)** | **198 (90%)** | **16%** | **0편** |
| 태그 + 신발×2 + 카테고리 0.3 | 193 (87%) | 18% | 0 |

읽히는 것 셋:

- **태그 IDF만으로 91%가 나온다.** 900개 1회성 태그는 버릴 대상이 아니라 주력 신호다
- **신발 링크 단독은 안 된다** — 신발 얘기가 없는 글 52편이 추천을 못 받는다
- **신발 가중치를 2배로 올리면 오히려 나빠진다**(90%→87%). 1:1이 맞다

### 3.3 추천 개수 3 → 6

| limit | 노출 편수 | 상위10 점유 | 추천 0 |
|---|---:|---:|---:|
| 3 | 198 (90%) | 16% | 0 |
| **6** | **216 (98%)** | **15%** | **0** |

6개면 미노출이 23편에서 **5편**으로 줄고, 3열 그리드 두 줄로 떨어져 레이아웃도 자연스럽다.

> 알고리즘과 개수를 같이 바꾸면 GA에서 효과가 섞인다. 다만 **알고리즘 효과는 GA 없이 결정적으로
> 측정된다**(위 표는 전부 오프라인 계산이다). GA에 섞이는 건 개수의 한계 효과뿐이라 감수한다.

### 3.4 성능 — 인덱스 메모이즈

221편 × 후보 221편을 페이지마다 계산하면 SSG 빌드에서 약 1,000만 번의 비교가 된다.
**IDF 테이블과 신발 링크 집합을 1회 구축해 모듈 스코프에 메모이즈한다.**
`buildShoeLinkIndex()`가 이미 쓰는 패턴을 그대로 따른다.

SSG 서버에서만 호출되므로 클라이언트 번들에는 영향이 없다
(메모리의 461KB 사례 — `'use client'` 컴포넌트가 모듈 스코프에서 데이터 getter를 부르면
풀데이터가 클라 번들에 실린다 — 를 재현하지 않도록 호출 위치를 서버로 유지한다).

| `src/lib/__tests__/blog-related.test.ts` | 점수 규칙 TDD + 커버리지 회귀 가드 |

**수정**

| 파일 | 변경 |
|---|---|
| `src/lib/data/blog/index.ts` | `getRelatedPosts`가 새 점수 사용, 기본 `limit` 3 → 6 |

`src/lib/blog/`는 이미 있다(`split-content.ts`). `related.ts`를 그 옆에 둔다.
`src/lib/marathon/`(`bands.ts`·`distance.ts`)이 같은 패턴의 선례다.

**상세 페이지는 건드리지 않는다.** 확인해 보니 호출이 `getRelatedPostsMeta(slug)`로 limit을
명시하지 않고, 그리드도 이미 `grid-cols-1 md:grid-cols-2 lg:grid-cols-3`이라 **6개가 자동으로
두 줄로 떨어진다.** 기본 limit만 바꾸면 된다.

`getRelatedPosts` / `getRelatedPostsMeta`의 **시그니처는 바꾸지 않는다** — 호출처가 그대로 돈다.

## 5. 검증

순수 함수라 **TDD로 규칙을 못 박는다.** 이 프로젝트에는 Vitest 유닛 테스트만 있고
(`src/lib/__tests__/`) RTL·jsdom이 없다 — 테스트 인프라 추가는 범위 밖이다(YAGNI).

**규칙 테스트**

| 단언 | 이유 |
|---|---|
| 희귀 태그 공유가 흔한 태그 공유보다 높은 점수 | IDF의 핵심 |
| 같은 신발을 링크하면 점수에 반영 | 이 사이트 고유 신호 |
| 태그·신발이 안 겹쳐도 같은 카테고리면 점수 > 0 | 추천 0 방지 |
| 점수 동점이면 최신 글이 앞 | 정렬 규칙 |
| 자기 자신은 결과에 없다 | 기본 |

**커버리지 회귀 가드** — 전체 221편에 대해 돌려 아래를 단언한다:

```
노출되는 글 ≥ 전체의 80%      (현재 12%, 설계 목표 98%)
상위 10편 점유 ≤ 30%          (현재 96%, 설계 목표 15%)
추천이 0개인 글 = 0편
```

임계값을 목표치(98%/15%)가 아니라 **여유 있는 값(80%/30%)**으로 잡는 이유: 글이 추가되면
수치가 자연히 흔들린다. 이 가드는 정확한 값을 지키는 게 아니라 **알고리즘이 다시 편중되는 것을
잡는 장치**다.

**검증 체인**: `npx tsc --noEmit` → `npm test` → `npm run lint` → `npm run validate` →
`set -o pipefail && npm run build`

빌드 시간이 유의미하게 늘어나면(§3.4 메모이즈 실패 신호) 그 자체가 결함이다 — 빌드 시간을 기록한다.

## 6. 제약

- **`git add`에 파일을 명시한다.** `-A`/`.`/`-a` 금지 — `tsconfig.tsbuildinfo`(빌드 산출물,
  git 추적 중)가 딸려 들어간다
- **검증은 `set -o pipefail`과 함께.** `npm run build | tail`이 실패 exit code를 삼킨 이력이 있다
- **이 셸은 zsh다.** 따옴표 없는 `$VAR`는 단어 분리되지 않는다
- **`getRelatedPosts`를 서버에서만 호출한다** — 클라이언트 컴포넌트가 모듈 스코프에서 부르면
  풀 블로그 데이터가 클라 번들에 실린다(실측 712KB 사례 있음)
- 상세 페이지의 in-article 광고 슬롯 로직을 건드리지 않는다(수익 동선)

## 7. 범위 밖

- **신발 상세 페이지의 관련글** — 측정 결과 건강하다: 노출 120편, 상위10 점유 32%,
  관련글 0인 신발 2종(2%). `curated + 본문 링크 기반 보충`이 실제로 관련 있는 신호로 작동한다.
  **없는 문제를 만들지 않는다**
- `/blog` 인덱스 개편 — 28일 조회 125로 노출면이 작다. 별도 판단
- 태그 1144개 정제 — 통제 어휘 15~20개로 줄이는 작업. 별도 스펙
- `tips` 카테고리 7편 문제
