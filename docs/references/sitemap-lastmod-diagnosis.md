# sitemap lastmod가 두 값으로 뭉쳐 있던 문제 (2026-09-04)

## 측정 사양

- **분석 단위**: sitemap URL 1건
- **모집단**: `https://allrunabout.com/sitemap-0.xml` 의 931개 전수 (배포본)
- **집계**: `<lastmod>` 문자열의 고유값 수 — **초 단위 원값**으로 센다
- **데이터 시점**: 2026-09-04
- **색인 상태 출처**: Search Console URL 검사 API 전수 조회

## 증상

배포된 사이트맵 931개 URL의 lastmod가 **고유값 2개**뿐이었다.

| 값 | 건수 | 정체 |
| --- | ---: | --- |
| `2026-09-04T07:31:26+09:00` | 665 | 저장소의 **최신 커밋 날짜**와 정확히 일치 |
| `2026-09-03T22:48:55.856Z` | 266 | `buildTime` (밀리초가 붙은 `toISOString()` 형식) |

경로별로 보면 `/blog` 263개가 통째로 `buildTime` 쪽이었고, 나머지는 최신 커밋 날짜였다.

## 원인 두 가지

**1. 배포 환경에 git 이력이 없다.**
`gitLastMod()` 는 `git log -1 --format=%cI -- <파일>` 로 파일별 마지막 커밋을 찾는다. 얕은 복제
(`--depth 1`)에는 커밋이 하나뿐이고 그 커밋이 전체 트리를 "추가"한 것으로 보이므로, **존재하는
모든 경로가 똑같이 최신 커밋 날짜를 돌려받는다.** 665개가 최신 커밋 날짜와 초 단위까지 일치하는
것이 그 증거다. 로컬(전체 이력)에서 같은 코드를 돌리면 값이 112개로 흩어진다.

**2. `/blog` 가 없는 파일을 가리키고 있었다.**
`lastModFor()` 가 `src/lib/data/blog/posts.ts` 를 보는데, 2026-07 분리로 그 파일은
`src/lib/data/blog/posts/` 폴더가 됐다. 없는 경로라 `git log` 가 빈 값을 주고 `buildTime` 으로
떨어졌다. 블로그 263개 전부가 여기 해당한다.

## 왜 문제인가

lastmod 는 크롤러가 "다시 올까"를 정할 때 보는 값이다. 모든 페이지가 배포할 때마다 "방금 바뀜"을
신고하면 그 값은 정보가 없어진다. 마침 이 사이트에는 **구글이 낡은 부정 판정을 들고 있는 페이지가
127개** 있었다 — noindex 제외 108, 404 12, soft 404 7로 분류돼 있는데 2026-09-04 전수 확인 결과
전부 HTTP 200에 `index, follow` 였다. 마지막 크롤이 117개는 2026-07이다. 즉 7월에 한 번 보고
판정한 뒤 다시 오지 않았고, "나 그 뒤에 고쳐졌다"고 말할 수단이 lastmod 인데 그게 망가져 있었다.

## 고친 방법

- **얕은 복제면 `git fetch --unshallow` 를 한 번 시도한다.** 실패해도 빌드는 계속한다.
- **`/blog` 는 글 데이터의 `updatedAt ?? publishedAt` 을 직접 쓴다.** 폴더를 훑어 slug→날짜 맵을
  만들므로 파일 구조가 또 바뀌어도 경로를 손으로 고칠 일이 없고, git 이력이 없는 환경에서도 읽힌다.
- **`/vs` 는 신발 두 켤레 중 더 최근 파일 날짜를 쓴다.** pairs.ts 한 파일을 보면 354개가 같은 날짜를
  받는다. 비교 페이지의 내용은 그 두 신발이므로 이쪽이 실제에 가깝다.
- **canary**: 생성된 lastmod 고유값이 5개 미만이면 빌드 로그에 경고한다. 빌드를 실패시키지는
  않는다. 이 사고가 몇 달간 안 잡힌 이유가 "사람 눈으로 sitemap.xml 을 봐도 날짜가 그럴듯해
  보여서"였기 때문이다.

### /marathon 후속 (같은 날 추가 수정)

처음에 "항목에 slug 필드가 없어 대응을 못 만든다"고 적었는데 **틀렸다.** 필드 이름이 `slug` 가
아니라 `id` 였고(`/marathon/[id]` 라우트), `slug:` 로만 찾아서 없다고 결론지은 것이다. 11개 월별
파일에서 id 115개가 전부 잡힌다. 그래서 디렉터리 → 월별 파일로 좁혔고 `/marathon` lastmod 가
1개 → 8개 값이 됐다(전체 고유값 112 → 119).

**이 변경은 단기 신호를 줄인다. 알고도 택했다.**

| | 디렉터리 날짜(넓음) | 월별 파일 날짜(좁음) |
| --- | ---: | ---: |
| 낡은 판정 127개 중 변경 신호 | 103 | **96** |
| /marathon lastmod 고유값 | 1 | **8** |

넓은 쪽이 7개를 더 신고하지만 그건 거짓이다 — 행사 하나를 고쳐도 115개가 전부 "우리 다 바뀌었다"고
말한다. 구글은 부정확한 lastmod 를 아예 무시할 수 있다고 밝히고 있어, 부풀린 7개 때문에 정직한
96개까지 같이 버려지는 쪽이 손해가 크다.

**템플릿 날짜(`src/app/(detail)/marathon/[id]/page.tsx`)를 max 로 섞지 않았다.** 그 파일이
2026-09-04 커밋이라 섞으면 115개가 도로 한 값이 된다. 템플릿 수정은 "중요한 콘텐츠 변경"이
아니므로 lastmod 의 근거로 쓰지 않는다.

신호를 잃은 7개는 데이터가 6~7월 이후 정말 안 바뀐 행사들이다. 이들의 낡은 판정은 lastmod 로
풀 문제가 아니라 개별 색인 요청 대상이다.

## 배포 후 실측 (2026-09-04)

배포 반영 확인. 라이브 `sitemap-0.xml` 의 lastmod 고유값 **2 → 112** 로, 로컬 전체 이력 실행과
같은 값이 나왔다. **`git fetch --unshallow` 가 Cloudflare 빌드 환경에서 통했다는 뜻이다**
(신발별 날짜처럼 이력이 있어야만 나오는 값들이 그대로 나왔다).

핵심 지표는 고유값 수가 아니라 "변경 신호가 실제로 생겼는가"다. 구글이 낡은 부정 판정을 든
127개에 대해 새 lastmod 와 마지막 크롤일을 대조했다.

| | 건수 |
| --- | ---: |
| lastmod > 마지막 크롤 — **변경 신호 있음** | **103** |
| lastmod ≤ 마지막 크롤 — 신호 없음(내용이 정말 안 바뀜) | 24 |

예: `/vs/adidas-supernova-rise-2-vs-hoka-clifton-10` 은 2026-06-01 크롤 이후 방치돼 있었는데
이제 lastmod 2026-08-11 을 신고한다.

**보장은 아니다.** lastmod 는 재크롤 근거를 주는 신호일 뿐 구글이 반드시 온다는 뜻이 아니다.
다음 회차 측정에서 볼 것은 이 103개의 `lastCrawlTime` 이 갱신되는지다.

## 배포 후 확인할 것

    curl -s https://allrunabout.com/sitemap-0.xml | grep -o '<lastmod>[^<]*</lastmod>' | sort -u | wc -l

2가 아니라 수십 이상이어야 한다. **2가 그대로면 `git fetch --unshallow` 가 배포 환경에서 실패한
것이다** — 그때는 날짜를 git 이 아니라 콘텐츠 데이터에서 읽는 쪽으로 더 옮겨야 한다.
