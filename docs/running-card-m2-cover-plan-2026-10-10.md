# 러닝카드 M2 단일 메달 표지 — 확정 실행 계획

상태: **계획 확정, 구현 전. 사용자가 모델을 전환한 뒤 구현을 시작한다.**

## 1. 사용자 결정과 작업 범위

2026-10-10 사용자 요청: 분석 카드는 현재 모습이 마음에 들므로 유지하고, 표지 이미지만 M2 시안 기반으로 고품질화한다. 두 선택지에 대해 “추천대로 갈게”라고 답했다.

- **표지의 메달은 원형 하나로 고정한다.** 목표별 외곽 변형은 적용하지 않는다.
- **인물을 상징하는 표식 하나를 중앙에 크게 새긴다.** 테두리는 절제된 장식만 사용한다. 거리·횟수·페이스·요일 등을 구슬 수, 물결, 끈 길이·무늬에 인코딩하지 않는다.
- 인물명·가문·칭호·문구는 메달 바깥의 표지 글자로 유지한다.
- 변경 대상은 저장·열기·공유하는 **첫 장 표지 PNG**다. 피드 1080×1350, 스토리 1080×1920 둘 다 적용한다.
- **두 번째 분석 PNG는 작은 7동전 메달을 포함해 그대로 보존한다.** 점수, 문구, 배치, 크기, 색상 모두 기준 이미지와 대조한다.
- 웹의 입력 7단계, 완성 메달, 웹 분석 결과 화면, 추천 신발·링크, 판정 알고리즘도 현행을 유지한다. 사용자 요청이 “표지 이미지만”이기 때문이다.
- 금·은·황동 선택은 새 표지에도 반영한다. 기본 마감은 현행 금이다.
- 새 표지는 개인 기록을 표시하지 않으므로 같은 인물·마감·크기에서 기록 숨김 ON/OFF가 같은 표지를 생성한다. 분석 카드의 숨김 동작은 현행대로다.

이 문서는 표지의 최신 결정이다. `running-card-s7-symbols-2026-10-10.md`에 기록된 7동전+중앙 명판은 기존 화면·분석 카드의 구현 기록이다. 그것을 표지의 최종 형태로 재해석하지 않는다.

## 2. M2에서 가져오는 것과 시각적 목표

원본: `.worktrees/running-input-v2/docs/running-input-studies-2026-10-01.md`의 M2(63행 부근), `study/running-input-v2` 브랜치의 같은 파일. M2는 **A 클래식의 면 + C의 두께감**, 중앙을 신화 인물 문장 자리로 남긴 단일 메달이었다. 원본 2D 시안의 렌더 품질을 복제하는 작업은 아니다.

목표는 **실물 기념 메달의 제품 사진처럼 보이는 표지**다.

- 원판: 밝은 새틴 금속 바탕, 얇은 단차 테두리, 옆면의 촘촘한 밀링, 실제 두께와 모따기. 중앙은 넓고 정돈된 면으로 둔다.
- 표식: 원판 지름의 약 45–55% 너비를 시작점으로 삼고 인물별 시각적 무게를 맞춘다. 바탕과 같은 금속 계열에 더 선명한 광택, 모따기 벽, 접합부 그림자를 사용한다. 평면 스티커처럼 보이면 실패다.
- 장식: 얇은 이중 테와 미세한 금속결 정도. 다중 로제트, 과도한 구슬 띠, 두꺼운 장식 테로 중앙 표식과 경쟁하지 않는다.
- 리본: 현행 주황색 계열의 짧은 직조 리본과 금속 고리. 메달이 주인공이며 리본이 그림 영역 대부분을 차지하지 않는다. 사용자 기록에 따라 길이가 달라지지 않는다.
- 카메라: 거의 정면, 두께가 읽히는 작은 고정 기울기. 표식이 찌그러질 정도의 원근은 금지한다.
- 조명: 큰 부드러운 주광과 제한된 윤곽광. 하이라이트가 표식을 지우거나 금색 면 전체가 검게 꺼지지 않도록 한다. 반사·거칠기·그림자로 금속감을 만든다.
- 배경·글자: 현행 잉크색 배경과 크림색 글자, 주황 강조색을 이어 간다. 메달 아래 인물명 → 칭호 → 문구의 위계를 유지한다. 새 폰트 도입은 필요 없다.
- 피드·스토리를 각각 조판한다. 스토리는 기존 상단 약 250px·하단 약 300px의 UI 가림 여유를 존중하고 실제 결과물에서 검수한다.

처음에는 헤파이스토스(망치), 아폴론(월계관), 제우스(독수리) 3개로 형태·곡선·복잡한 실루엣을 검증한다. 같은 조명과 배율로 나란히 보아야 한다. 세 장의 부조 품질이 만족스러워진 뒤 36명으로 확장한다.

## 3. 구현 경계 — 분석 카드 보존이 우선

현재 `medal3d-flow.js`의 `shareImage()`는 cover와 analysis 모두 `renderFigure()`로 같은 7동전 메달을 그린다. `drawResultMedal()`도 이를 사용한다. **공용 `renderFigure()`나 기존 메달 본체를 단일 메달로 바꾸면 범위 위반**이다.

권장 구현:

1. 표지 전용 모듈을 추가한다(예: `src/components/running-card/medal/medal-cover-renderer.js`). 기존 three.js와 절차형 금속·부조 방식을 이용해 단일 원판을 만든다. 신규 렌더 라이브러리나 GLB 생성 서비스는 필요하지 않다.
2. 기존 `CHARACTER_SIGNS`의 인물 ID와 도상 의미를 재사용한다. 중앙 명판 전체를 확대하지 않는다. 표지용 고해상도 마스크·부조를 만들고 큰 크기에서 선 두께와 곡선 품질을 검수한다. 공용 표식 도형을 바꾸면 분석 이미지도 바뀌므로 필요한 보정은 표지 안에서 처리한다.
3. 표지 전용 씬·카메라·재질을 사용한다. 초기 접근은 저장 때만 렌더러를 만들고 결과 캔버스를 얻은 뒤 GPU 자원을 해제하는 방식이다. 기존 화면의 씬·조명·카메라·재질을 교체하지 않는다. 성능 측정 없이 전역 캐시나 상시 WebGL 컨텍스트를 추가하지 않는다.
4. `shareImage()`의 `page === 'cover'` 분기에서만 지연 로딩해 표지용 투명 캔버스를 먼저 생성한다. `drawCover()`의 동기 그림 콜백에는 이 캔버스를 합성하는 함수를 전달한다. `drawAnalysis()`와 기존 `renderFigure()`는 현행 경로를 사용한다.
5. `medal3d-share.js`의 `drawCover()` 안에서 메달 영역·조판만 필요에 맞게 조절한다. 공용 `TH`, `M`, `TOP`, `FOOT`, `masthead`, `address`의 변경은 분석 이미지에도 영향을 주므로 피한다. 표지 전용 값이 필요하면 표지 함수에 둔다.
6. 인물 ID는 판정된 `plate.figure.id` 등 현재 흐름의 식별자를 사용한다. 이름 문자열로 역추론하지 않는다. 렌더 시작 시 인물·마감·크기를 캡처하고, 완료 후 `destroyed`를 확인한다. 저장 도중 다시 시작한 경우 오래된 결과를 전달하지 않는다.
7. WebGL을 사용할 수 없으면 **동일한 원판과 표식**의 2D 부조 대체 렌더를 제공한다. 고해상도 마스크·노멀 기반 음영을 활용한다. 7동전 메달이나 인물 사진으로 되돌아가면 안 된다.

기존 폰트 로딩, PNG Blob 반환, 파일 이름, 네이티브 공유, 새 탭 열기, 결과 URL 처리는 유지한다. 표지 렌더가 늦거나 실패하면 기존 오류 상태를 통해 재시도할 수 있어야 한다. 루트 리팩터링·죽은 코드 정리는 이번 범위가 아니다.

## 4. 실행 순서와 각 단계의 확인

### A. 기준 이미지 확보

- 현재 커밋 기준으로 피드/스토리 × 기록 표시/숨김의 분석 PNG 4개를 새로 저장한다. 기존 증거는 아래 경로에 있으나 임시 파일만을 유일한 기준으로 삼지 않는다.
- 웹 결과 화면과 공유 UI도 모바일 390×844 및 375×667로 캡처한다.
- 같은 브라우저·글꼴·렌더 조건에서 변경 전후 픽셀을 비교한다. 동일 조건에서 차이가 나면 분석 카드 보존 실패 원인을 확인한다.
- 근거: 분석 PNG 생성 직전에 cover가 실행되므로, 표지 렌더가 공용 GPU 상태를 오염시키는지도 cover→analysis 순서로 확인해야 한다.

### B. 세 인물 표지 시안

- 단일 원판, 표지용 조명·리본·부조를 구현하고 세 인물의 피드/스토리 총 6장을 실제 PNG로 만든다.
- 1080px 원본 확대와 390px 축소본 모두 시각 검수한다. 조명·부조 깊이·테두리 두께를 여기서 조정한다.
- 시안은 실제 최종 렌더 경로에서 생성한다. 구현할 수 없는 별도 목업을 완성품처럼 제시하지 않는다.
- 최초 검토물로 세 인물 표지를 사용자에게 보여줄 수 있도록 저장한다. 추가 결정을 요구하는 새로운 모호함이 없으면 승인 요청을 반복하지 않고 계획 범위 안에서 이어 간다.

### C. 전 인물·저장 동작 연결

- 36명 전체의 원형 메달을 접촉 시트로 검수하고, 극단적으로 넓거나 가는 표식의 광학 크기를 조절한다.
- 36명 × 피드/스토리 표지를 전수 생성해 누락·빈 그림·긴 이름·문구 잘림을 확인한다. 세 마감의 시각 품질은 세 대표 인물로 우선 검증하고 문제 발견 시 해당 범위를 넓힌다.
- 실제 UI의 표지만 저장, 2장 저장, 각각 열기, 기록 숨김 전환, 금/은/황동 변경, 저장 없이 다시 열기, 다시 입력 후 다른 인물 판정을 검증한다.
- 기존 링크·신발 추천 경로의 정상 동작도 사용자 흐름에서 확인한다.

### D. 검증·완료

- 코드 테스트는 표식 ID 누락, 같은 인물·마감의 결정성, 표지에 개인 기록이 새지 않는 조건, 렌더 해제 후 재생성 등 실제 회귀 위험에 집중한다. 단순 도형 명령을 복사한 테스트는 만들지 않는다.
- 테스트를 변경했으면 `npm test` → `npm run build`. 코드 변경 시에도 `npm run build`는 필수다.
- 분석 PNG 비교, 모바일 화면, WebGL 없는 환경의 단일 메달, 콘솔 오류, 실제 저장 PNG와 현재 설정 일치를 검사한다.
- 표지 생성 시간과 반복 생성 후 컨텍스트/메모리 해제를 측정한다. 입력 단계의 초기 로딩에 새 렌더 모듈이 포함되지 않았는지 빌드 출력에서 확인한다.
- QA 결과와 최종 표지 예시를 문서로 남기고 worktree에서 커밋·ship한다. CI/Cloudflare 배포 성공 후 실제 사이트의 표지 저장과 분석 보존을 최종 확인한다.
